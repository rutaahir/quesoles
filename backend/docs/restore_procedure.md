# Database Restore Procedure (RPO: 24h, RTO: 4h)

This document describes the step-by-step procedure to restore the database from a backup file generated by the `run_mysql_backup` task.

## Prerequisites

1. Access to the target database server.
2. A database user with full privileges (`CREATE`, `DROP`, `INSERT`, `SELECT`, etc.) on the target schema.
3. The compressed backup file (`.sql.gz`) stored in the `backups/` directory or downloaded from S3 storage.
4. Python 3.x and Django virtual environment activated.

---

## Step 1: Locate the Backup File

Backups are named in the format: `backup_[database_name]_[timestamp].sql.gz`.
Verify that you have the most recent backup:
```bash
ls -lh d:\queue-flow-main\Quesols\backend\backups\
```

---

## Step 2: Uncompress the Backup File

Uncompress the target backup file to extract the raw SQL dump:
```bash
# On Linux/macOS
gunzip -k backups/backup_queuing_solutions_20260816_120000.sql.gz

# On Windows (PowerShell)
# You can use standard tools like 7-Zip, or execute:
Expand-Archive -Path backups/backup_queuing_solutions_20260816_120000.sql.gz -DestinationPath backups/
```

---

## Step 3: Clear the Target Database (Or Create a Fresh One)

> [!CAUTION]
> This will destroy all existing data in the target schema. Ensure you are importing into the correct environment.

Login to the MySQL/MariaDB shell and recreate the schema:
```sql
DROP DATABASE IF EXISTS queuing_solutions;
CREATE DATABASE queuing_solutions CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

---

## Step 4: Import the SQL Dump

Execute the SQL script against the fresh database:
```bash
# On standard environments
mysql -h 127.0.0.1 -u root -p queuing_solutions < backups/backup_queuing_solutions_20260816_120000.sql
```

If using docker-compose:
```bash
docker exec -i queuing_solutions_db mysql -u root -proot@123 queuing_solutions < backups/backup_queuing_solutions_20260816_120000.sql
```

---

## Step 5: Fake Initial Django Migrations

Because the dump contains the exact tables and columns generated by migrations, running standard Django migrations on a fresh schema after import might fail (since it tries to create already existing tables).

To sync Django's migration history table, run:
```bash
python manage.py migrate --fake-initial
```

---

## Step 6: Verify Data Integrity

Log into the django console or run checks to verify row counts:
```bash
python manage.py shell
```

Verify model counts in python:
```python
from companies.models import Company
from queuing.models import Ticket
print("Companies:", Company.objects.count())
print("Tickets:", Ticket.objects.count())
```
Ensure counts match the logs recorded in the audit trail at the time of backup.
